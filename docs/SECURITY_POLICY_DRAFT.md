# セキュリティポリシー（草稿）
## 手描きでスタンプメーカー — Google OAuth 本番環境移行対応

> **文書ステータス:** 草稿 (DRAFT)
> **最終更新日:** 2026年8月29日
> **対象システム:** 手描きでスタンプメーカー（LINE スタンプ制作 Web アプリケーション）

---

## 1. 本文書の目的

本文書は「手描きでスタンプメーカー」が Google OAuth 2.0 認証を本番環境で使用するにあたり、Google の OAuth アプリ審査（Verification）要件を満たすためのセキュリティポリシーを定めるものである。

Google の OAuth 本番移行審査では、以下の 3 点の提出が求められる：

1. **プライバシーポリシー**（セクション 3）
2. **OAuth スコープの使用目的の正当性**（セクション 5）
3. **データの取扱いとセキュリティ対策**（セクション 4, 6, 7）

---

## 2. システム概要

### 2.1 サービスの説明

手描きの線画から AI（Google Gemini API）を活用し、LINE スタンプ画像を自動生成する Web アプリケーション。

### 2.2 技術スタック

| レイヤー | 技術 |
| --- | --- |
| フロントエンド | React 19 + TypeScript + Tailwind CSS（Vite） |
| バックエンド / DB | Supabase（PostgreSQL + Row Level Security） |
| 認証基盤 | Supabase Auth（Google OAuth 2.0 連携予定） |
| AI 画像生成 | Google Gemini API（gemini-3.1-flash-image） |
| ホスティング | ※ 本番環境のホスティング先を記入 |

### 2.3 データフロー概要

```
ユーザー（ブラウザ）
  │
  ├─ Google OAuth 2.0 ──→ Supabase Auth ──→ JWT トークン発行
  │
  ├─ 線画アップロード / 描画
  │
  ├─ Gemini API 呼び出し（画像生成）
  │
  └─ Supabase DB（プロジェクト・画像データ保存）
```

## 3. プライバシーポリシー

> **実装済み:** プライバシーポリシーページを `/privacy.html` に公開済み。

### 3.1 収集する情報

本サービスは、Google OAuth 認証を通じて以下の情報を取得する。

| 情報の種類 | Google OAuth スコープ | 用途 |
| --- | --- | --- |
| メールアドレス | `email` | 利用可能ユーザーの識別（nua.ac.jp ドメイン確認）・ログイン |
| 表示名 | `profile`（openid） | アプリ内でのユーザー名表示 |
| プロフィール画像 URL | `profile`（openid） | アプリ内でのアバター表示（任意） |

上記以外の Google アカウント情報（連絡先、カレンダー、ドライブ等）には一切アクセスしない。

### 3.2 ユーザーが作成するデータ

| データの種類 | 説明 | 保存先 |
| --- | --- | --- |
| 線画データ | ユーザーが描画またはアップロードした画像 | Supabase DB |
| 生成画像 | AI が生成したスタンプ画像（Base64） | Supabase DB |
| プロジェクト設定 | スタイル選択、プロンプト、ステップ状態等 | Supabase DB |

### 3.3 データの利用目的

- **利用可能ユーザーの識別:** メールアドレスのドメイン（nua.ac.jp）を確認し、名古屋芸術大学に所属するユーザーのみにサービスを提供する
- **生成画像とユーザーの紐づけ:** ユーザーが生成した画像をデータベース上でユーザーアカウントと紐づけ、プロジェクトの保存・復元を可能にする
- AI 画像生成のため、ユーザーの線画データを Google Gemini API に送信する（生成処理のみ。Google 側の利用規約に準拠）
- ユーザーの個人情報を第三者に販売、貸与、共有しない
- 広告目的でのデータ利用は行わない

### 3.4 データの保管

- すべてのユーザーデータは Supabase（AWS インフラストラクチャ上）に保管する
- データベースへのアクセスは Row Level Security（RLS）により、認証済みユーザー自身のデータのみに制限する（※現在 anon アクセス。OAuth 実装時に `authenticated` + `auth.uid()` ベースに移行する。セクション 8 参照）
- 通信は全経路で TLS 1.2 以上を使用する

### 3.5 データの保持と削除

- **自動削除ルール:** 最終アクセス日から **30日間** ログインがない場合、そのユーザーに関連するすべてのデータ（プロジェクト・画像・ログイン履歴・認証情報）が自動的に削除される。削除されたデータの復元はできない
- ユーザーはアプリ内の操作でプロジェクトおよび画像データをいつでも手動削除できる
- アカウント全体の即時削除を希望する場合、※ 連絡先メールアドレスを記入 へ連絡することで対応する
- サービス終了時は、全ユーザーに 30 日前に通知し、その後すべてのデータを削除する

### 3.6 Cookie とローカルストレージ

- 認証セッション管理のために Supabase Auth が Cookie / localStorage を使用する
- アクティブなプロジェクト ID の記憶にのみ localStorage を使用する（キー: `current_project_id`）
- トラッキング目的の Cookie は使用しない

## 4. データセキュリティ対策

### 4.1 認証・認可

| 対策 | 実装状況 | 備考 |
| --- | --- | --- |
| Google OAuth 2.0（PKCE フロー） | **予定** | Supabase Auth 経由 |
| JWT トークンベースのセッション管理 | **予定** | Supabase が自動管理 |
| Row Level Security（RLS） | **実装済** | 全テーブルで有効 |
| ユーザー単位のデータ分離 | **予定** | `user_id` + `auth.uid()` ポリシーに移行 |
| API キーの秘匿 | **実装済** | 環境変数で管理、クライアントに公開しない |

### 4.2 通信の保護

- Supabase エンドポイント: HTTPS（TLS 1.2+）必須
- Gemini API 通信: HTTPS（TLS 1.2+）必須
- HTTP Strict Transport Security（HSTS）ヘッダーを設定する

### 4.3 入力値の検証

- データベース側で `CHECK` 制約を使用（`image_type` の enum バリデーション等）
- ユーザー入力のプロンプトテキストは、Gemini API にそのまま渡す前にサニタイズしない（AI プロンプトとして意図された入力のため）が、HTML レンダリング時に React の自動エスケープにより XSS を防止する
- ファイルアップロードは画像形式（JPEG, PNG）に制限する

### 4.4 依存パッケージの管理

- `package-lock.json` によるバージョン固定
- 定期的な `npm audit` の実施
- 重大な脆弱性が報告されたパッケージは速やかにアップデートする

## 5. OAuth スコープの正当性

### 5.1 要求するスコープ

| スコープ | 分類 | 正当性 |
| --- | --- | --- |
| `openid` | 基本 | ユーザーの一意識別子の取得（認証に必須） |
| `email` | 基本 | アカウント識別・通知送信・サポート対応 |
| `profile` | 基本 | ユーザー名表示によるパーソナライズ |

### 5.2 スコープの最小化

- センシティブスコープ（Sensitive Scopes）や制限付きスコープ（Restricted Scopes）は要求しない
- Google ドライブ、Gmail、カレンダー等のデータにはアクセスしない
- 取得した情報はログイン・表示目的のみに使用し、外部サービスへの転送は行わない

## 6. インシデント対応計画

### 6.1 セキュリティインシデントの定義

以下の事象をセキュリティインシデントと定義する：

1. ユーザーデータへの不正アクセス（または不正アクセスの疑い）
2. データの漏洩・改ざん・紛失
3. 認証システムの障害・乗っ取り
4. サービスの可用性に影響する攻撃（DDoS 等）

### 6.2 対応手順

| フェーズ | 対応内容 | 目標時間 |
| --- | --- | --- |
| 検知 | Supabase ログ監視、異常アクセスパターンの検知 | 即時 |
| 封じ込め | 該当アカウントの一時停止、API キーの無効化 | 1 時間以内 |
| 通知 | 影響を受けたユーザーへのメール通知 | 24 時間以内 |
| 復旧 | 脆弱性の修正、システム復元 | 72 時間以内 |
| 事後分析 | 原因分析と再発防止策の策定・公開 | 2 週間以内 |

### 6.3 連絡窓口

- セキュリティに関する報告: ※ security@example.com を記入
- 一般的な問い合わせ: ※ support@example.com を記入

## 7. アクセス制御と運用管理

### 7.1 管理者アクセス

| 対象 | アクセス権限 | 認証方式 |
| --- | --- | --- |
| Supabase ダッシュボード | DB 管理・RLS 設定 | Supabase アカウント（MFA 推奨） |
| Google Cloud Console | OAuth 設定・API キー管理 | Google アカウント（MFA 必須） |
| ホスティングサービス | デプロイ・環境変数管理 | ※ サービス固有の認証 |

### 7.2 API キーの管理

- `VITE_SUPABASE_ANON_KEY`: クライアント側で使用（RLS により権限制御）
- `SUPABASE_SERVICE_ROLE_KEY`: サーバー側のみ（環境変数、クライアントに露出禁止）
- `VITE_GEMINI_API_KEY`: クライアント側で使用（※本番ではエッジファンクション経由のプロキシに移行を推奨。セクション 9 参照）
- Google OAuth Client Secret: Supabase Auth 側で管理（クライアントに露出しない）

### 7.3 ログと監査

- Supabase の組み込みログ機能でデータベースアクセスを記録する
- 認証イベント（ログイン・ログアウト・失敗）は Supabase Auth が自動記録する
- 異常なアクセスパターン（短時間での大量リクエスト等）を監視する

## 8. OAuth 本番移行時の必須対応事項

> **重要:** 以下は現在のシステムから本番 OAuth に移行する際に実装が必要な項目。

### 8.1 データベースの認可強化（必須・最優先）

**現状の問題:** RLS ポリシーが `USING (true)` で全データ公開状態。

**対応内容:**

1. `projects` テーブルに `user_id uuid NOT NULL DEFAULT auth.uid()` カラムを追加
2. `project_images` テーブルは `projects` 経由の所有権チェックに変更
3. RLS ポリシーを `auth.uid() = user_id` ベースに全面書き換え
4. `anon` ロールからの書き込み権限を削除

### 8.2 認証 UI の実装（必須）

- Google ログイン / サインアップ画面の実装
- 未認証ユーザーのリダイレクト処理
- セッション切れ時の再認証フロー
- ログアウト機能

### 8.3 Gemini API キーの保護（強く推奨）

**現状の問題:** `VITE_GEMINI_API_KEY` がクライアント側コードに含まれ、ブラウザの開発者ツールから閲覧可能。

**対応内容:**

- Supabase Edge Function を作成し、Gemini API 呼び出しをサーバー側にプロキシする
- API キーをエッジファンクションの環境変数（シークレット）に移動する
- クライアントからはエッジファンクション経由でのみ画像生成を行う

### 8.4 Google Cloud Console の設定

1. OAuth 同意画面の設定（アプリ名、ロゴ、プライバシーポリシー URL、利用規約 URL）
2. 承認済みリダイレクト URI に Supabase のコールバック URL を登録
3. OAuth クライアント ID / シークレットを Supabase Auth の Google プロバイダに設定
4. 審査申請の提出

## 10. 利用規約（要約）

> **注:** 正式な利用規約は別文書として作成し、公開 URL でホストすること。

- 本サービスは LINE スタンプ制作の支援を目的とする
- AI 生成画像の著作権・利用権はユーザーに帰属する（※法的確認が必要）
- サービスの悪用（不正アクセスの試行、大量の自動リクエスト等）を禁止する
- サービスの一時停止・終了の可能性があることを明記する
- 免責事項（AI 生成結果の品質保証はしない等）を含める

## 付録 B: 用語集

| 用語 | 説明 |
| --- | --- |
| RLS | Row Level Security。データベースの行単位のアクセス制御機構 |
| JWT | JSON Web Token。認証情報を含むトークン形式 |
| PKCE | Proof Key for Code Exchange。OAuth 2.0 の安全な認証フロー |
| MFA | Multi-Factor Authentication。多要素認証 |
| TLS | Transport Layer Security。通信の暗号化プロトコル |
| anon key | Supabase のクライアント向け公開鍵。RLS による権限制御下で使用 |
